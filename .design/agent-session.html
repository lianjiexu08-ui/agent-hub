设计方案 · Agent Hub

智能体会话

让两个智能体围绕一个议题多轮往返，最后收敛出一条能落地的结论。不是聊天，是一次有预算、有轮次、有终止条件的技术讨论。

状态：设计稿 范围：运行时 · 工具 · 存储 · 界面 前置：call_agent、消息总线、ask_agent

01 现有三条通道，各缺一块

Hub 已经有三种智能体间的通信方式。它们覆盖了「派活」和「广播」，但都不支持「讨论」。

通道形态缺什么
call_agent 同步委派。父任务提交子任务并阻塞等待，拿到最终结果就继续。 只有一问一答。对方没有机会反问，发起方也没法追问。
publish / read_topic 异步广播。订阅主题的智能体被唤醒成新任务，各自处理。 没有会话状态。谁被唤醒、回不回、回到哪个话题，全靠智能体自觉。
ask_agent 管家直接问某个智能体，拿回一条回复。 单轮，且结果只留在管家对话里，不进项目。

真正需要多轮的场景很具体：架构师和前端就接口边界来回确认；测试复现不了，开发要问清楚环境；评审方对一处改动有异议，作者需要解释两轮。这些都不是「派个活」能解决的。

02 四条设计原则

01
有界
轮次、时间、token 三重上限，任何一重触发都强制收敛。开一个会话不能变成打开一个无底洞。
02
串行
同一个会话在同一时刻只有一个智能体在说话。交替发言，天然避免两边同时改同一份上下文。
03
可审计
每一轮消息落库，带发言人、轮次、耗时。事后能回放，也能作为工作项的决策依据。
04
产出是结论，不是记录
会话结束必须给一条结论。记录留档，结论进工作项评论或转成新工作项。

03 核心模型

两个实体，没有第三个。会话是容器，消息是内容。

字段类型说明
idstrings_ 前缀的短 id
topicstring一句话议题，写进每轮提示，防止话题漂移
participantsstring[2]恰好两个发言方。多方自由讨论不在本期
turnnumber已进行的轮次
maxTurnsnumber默认 6，硬上限 12
deadlinestringISO 时间，默认 15 分钟
tokenBudgetnumber整场会话的 token 上限，默认 60k
tokensUsednumber累计用量，由每轮任务回填
statusenumopen / closed / aborted
conclusionstring?结束时的结论正文
endReasonenumconclusion / max_turns / deadline / budget / human
issueIdnumber?关联的工作项，会话由此发起时必填

消息表只加三列：sessionId、turn、from。复用现有的 comments 存储结构，只是挂到会话上而不是工作项上。

04 生命周期

open → 轮流发言 → closed · 有结论 aborted · 触达上限

结束时必须带上 endReason。触达上限的中止不是失败——它同样要求最后一位发言者给出「已讨论到什么程度、还差什么」的结论，而不是直接截断。

关键约定

最后一轮由系统注入硬提示：「这是最后一轮，必须给出结论，不能提出新问题。」结论可以为空泛，但必须存在。

05 协议：三个工具

智能体不直接操作会话表，只通过工具。所有工具都要求显式说明「接下来该谁说话」，避免含糊。

open_session({
  agent: "architect",          // 对话对象
  topic: "订单接口是否拆成两个端点",
  opening: "完整开场，含背景与你的初步立场",
  maxTurns?: 6,
  deadlineMinutes?: 15
}) → { session, turn, reply }   // 同步等到对方第一次回应

reply_session({
  session: "s_ab12",
  text: "针对你提的兼容性问题，我的判断是…",
  next: "architect" | null      // null 表示我认为可以结束了
}) → { session, turn, reply? }  // 给了 next 就等下一轮

close_session({
  session: "s_ab12",
  conclusion: "结论正文：决定是什么、依据是什么、还有哪些未决"
}) → { session }
}

每轮必须包含三样东西

  • 回应：对上一轮的具体回应，不能自顾自说。
  • 立场：同意 / 反对 / 有条件同意，三选一，不允许模糊。
  • 下一步：明确点名下一位发言方，或提出结束。

工具描述里把这三条写成硬要求。这是让对话收敛的主要手段——没有它，两个模型会互相客套二十轮。

06 调度

会话消息不是直接投递给模型，而是转成一次普通任务，复用现有的并发、优先级和成本体系。

  1. 对方被唤醒时，source 标记为 session，优先级继承发起任务。
  2. 任务输入 = 议题 + 最近 4 轮消息 + 你的角色 + 剩余轮次 + 本轮要求。
  3. 同一会话加锁（runningSession 集合），上一个任务没结束就不再提交下一个。
  4. 任务完成后，若调用了 reply_session 且给了 next，自动提交下一轮。
## 会话 s_ab12 · 第 3/6 轮
议题：订单接口是否拆成两个端点
你是：frontend-dev

[architect · 第2轮]
拆成两个端点会让前端多一次请求，但能独立缓存…

[你 · 第1轮]
从调用方看，我更希望保持单端点…

请回应上一位发言，然后二选一：
- reply_session(next="architect") 继续讨论
- close_session(conclusion="…") 达成结论

这是第 3 轮，还剩 3 轮。

07 成本与安全

三重封顶，任一触发即中止

轮次 默认 6，硬上限 12 —— 每轮至少一次模型调用，这是最直接的成本闸。
时间 默认 15 分钟 —— 防止某一方挂住不返回。
Token 默认 60k —— 从项目预算里扣，超了立刻中止并记录已用量。

  • 会话不计入工作项的 cost，单独记在会话上，避免污染单卡成本。
  • 不允许跨项目开会话：参与双方必须属于同一项目上下文，防止把 A 项目的背景泄露给 B 项目的人。
  • 会话内容写进调用记录（receipt），和普通任务一样可追溯。
  • 人随时可以终止：界面上一个「结束」按钮，走 human 原因，并要求补一条结论。

08 界面

不做独立的一级页面。会话挂在发起它的工作项上，作为时间线里的一段。

  • 工作项详情里，会话显示为一组可折叠的对话块，每轮带发言人头像与轮次标记。
  • 结束的会话只保留结论，正文默认折叠——它是过程，不是结论。
  • 管家发起或参与的会话，同样在管家对话里显示一张卡片，点开跳回工作项。
  • 进行中的会话有明确状态：第 3/6 轮 · 已用 12k tokens，让人知道还剩多少余地。

09 分阶段

P0
两方往返，最小可用
会话表 + 三个工具 + 串行锁。只支持固定 6 轮，没有 UI，靠调用记录查看。
P1
预算与可见性
token 预算、时间上限、工作项时间线、终止原因展示。
P2
人工介入
界面上插话、中止、手动延长轮次。人在环里，会话不再是黑盒。
P3
多方与主持人
引入主持人角色协调三方以上讨论。这一阶段才考虑「群聊」，且必须有强制的发言权轮转。

10 明确不做

—
不做开放群聊
三方以上自由发言在模型上几乎必然发散，收敛成本远高于收益。P3 之前不碰。
—
不替代 call_agent
简单委派继续用一问一答，便宜且快。会话只在「需要对方反问」时才值得开。
—
不自动开场
会话必须由智能体或人显式发起。系统不根据「有分歧」去猜该不该开会话——猜错的成本是白烧 token。
—
不建议 CLI 底座跑会话
Claude Code 这类底座单轮延迟以十秒计，六轮就是一分钟以上。会话默认走内置模型，CLI 底座只做最终执行。
与现有 call_agent、消息总线、ask_agent 并存，不替换。落地顺序见第 09 节。

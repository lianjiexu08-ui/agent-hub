# 实战问题日志：用 Agent Hub 开发 Speech2Ticket

用 Agent Hub 从零开发「AI 语音工单中台」（仓库 `lianjiexu08-ui/Speech2Ticket`），
把过程中遇到的 bug、卡点和难用的地方记在这里：现象 → 原因 → 处理。

状态：✅ 已修复　🔧 处理中　📝 记录待办

## 问题清单

### 1. ✅ 测试阶段的 tester 看不到代码

- **现象**：生命周期的「测试」阶段由 tester 智能体验收。tester 用 CLI 底座时，工作目录是一个空的临时目录，既看不到开发分支的代码，也跑不了测试命令，只能凭交付说明「核对」。
- **原因**：测试任务提交时不挂工作项（挂了会被当成工作项的主运行，触发完结逻辑），CLI 底座按 `task.issueId` 找 worktree，自然找不到。
- **处理**：CLI 底座对测试任务按测试记录反查被测工作项，在它的 worktree 里运行；测试提示词要求只读（可以装依赖、跑测试，不能改文件）。

### 2. ✅ 没有「依赖」：拆好的计划只能人工一项项放行

- **现象**：管家把第一期拆成 16 个有先后顺序的工作项（02 依赖 01、07 依赖 03/05/06……）。但 Agent Hub 里工作项一指派、设为待办就立刻开跑，没法表达「等 01 合并后再开始 02」。要么全部放在待规划里由人逐个放行，要么同时开跑、互相冲突。
- **处理**：工作项增加依赖（`dependsOn`）。
  - 依赖全部完成，或 PR 已合并（代码进了主干）才算满足；不满足时停在待办并说明在等谁，满足后自动开始。
  - 指派触发、负责人分诊、Linear 自动执行都经过同一个启动入口，统一把关；人手动「运行」也会被拦下并提示。
  - 拒绝依赖自己、跨项目依赖和循环依赖。
  - 管家的拆分计划可以按序号声明依赖，创建时换成工作项编号；智能体的 `create_issue` / `update_issue` 支持 `depends_on`。
  - 界面：看板卡片显示「⏸ 等依赖」，详情页可查看和编辑依赖。

### 3. ✅ 锁文件让项目骨架必定被「改动行数上限」拦下

- **现象**：安全护栏默认改动超过 800 行不自动合并。从零搭的项目会提交 `package-lock.json`、`uv.lock` 等锁文件，动辄几千行。
- **处理**：改动行数按 `git diff --numstat` 逐文件统计，锁文件和压缩产物不计入，单独在 PR 评论里列出。

### 4. ✅ 管家长回复期间没有任何进度提示

- **现象**：让管家读 1.8 万字的方案并拆计划，用了 2 分 13 秒。这期间界面只有「思考中」，看不到它在读文件、调工具还是卡住了。
- **处理**：管家处理消息时记录进度：每次工具调用（查看项目、查看 S2T-3、整理拆分计划（16 项）、请某个智能体帮忙……），以及调工具前说的话，实时显示在「正在处理 · N 秒」上方。API 和本机 Claude Code 两条通道都支持；从别的页面或接口发起的消息，在首页也能看到进度。
- **还可以做**：最终回复逐字流式输出（需要 Claude Code 的 `--include-partial-messages`）。

### 5. ✅ 没有模型 API Key 时，内置底座的智能体会直接失败

- **现象**：种子里的产品经理、架构师、测试、评审、项目负责人都用内置底座（需要 API Key）。本机只登录了 Claude Code 时，这些智能体一跑就鉴权失败，只能逐个手动改成 Claude Code。
- **处理**：设置页「运行底座」在内置底座缺凭据、本机又有已登录的 CLI 时，列出受影响的智能体，并提供「全部改用 Claude Code」一键切换（接口 `studio.switchRuntime`）。

### 6. ✅ 重启 Hub 后，旧的 CLI 进程还在改 worktree

- **现象**：CLI 底座的子进程以独立进程组启动，Hub 退出时既不结束它们，也没有记录。重启后旧的 Claude Code 继续在 worktree 里写代码；新 Hub 把那次运行标成「因重启中断」，哨兵随即重试，又在同一个 worktree 里起一个新进程，两个智能体同时改同一份代码。
- **处理**：CliRunner 登记每个子进程，并把进程号落盘。Hub 正常退出或重启时，结束这些进程的整个进程组；启动时再按落盘记录清理一次，覆盖 Hub 被强杀、崩溃的情况。清理前核对进程命令，避免误杀复用了同一进程号的无关进程。

### 7. ✅ 改了 Hub 代码只能「硬重启」，会打断正在跑的智能体

- **现象**：用 Agent Hub 开发项目、同时改 Agent Hub 自己时，每次重启都会中断运行中的智能体。哨兵会自动重试，但那一轮的模型调用就白费了。另外原来的重启按钮在旧进程退出前就轮询到 `/health` 200，会过早提示「已重启」。
- **处理**：
  - 设置页提供「空闲时重启」：先暂停开始新的工作项运行（进行中的生命周期、测试照常），等运行中的工作项都结束再重启；被挂起的工作项在新进程里自动开始，等待期间可以取消。原来的按钮改为「立即重启」，有运行中的工作项时会提示会中断几个。
  - `/health` 返回本次启动时间，前端以它变化为准判断重启完成。

### 8. ✅ Linear 自动执行：两次触发挨得太近时，后一次被丢掉

- **现象**：同步 Linear、修改自动执行设置都会触发一次「按范围过一遍」。前一次还没跑完时，后一次直接放弃；如果后一次恰好是关键的那次（比如刚把 Todo 加进范围），对应的 issue 就没人接手。是在全量测试并行跑、机器负载高时偶发暴露的。
- **处理**：正在跑时记一笔，跑完补跑一次。顺带把一个依赖时序的测试改稳。

### 9. ✅ 测试用例抄的是「要做的事」，不是验收标准

- **现象**：S2T-1 的测试用例是「目录：backend/…」「后端：用 pyproject…」这类实现步骤，真正的验收标准（`make test` 通过、`/healthz` 返回 200、CI 通过）一条都没进用例。
- **原因**：验收标准是从描述里抽「所有列表行」取前 6 条，排在前面的「要做的事」就被当成了验收标准。
- **处理**：描述里有「验收标准 / 验收条件」小节时只取该小节（支持【】、Markdown 标题、冒号三种写法），最多 10 条；没有小节时才退回全文列表。

### 10. ✅ 没地方打开也生成浏览器用例

- **现象**：S2T-1 是项目骨架，没有可访问的测试环境，测试用例却全是「浏览器验收」，还多一条「页面健康检查」。检查型用例的步骤固定写着 `pnpm vitest`，对 Python 项目没有意义。
- **原因**：只要描述里出现「前端」「页面」等词就判定为网页类任务。
- **处理**：真实模式下只有项目配置了测试地址、且装有 DevEye 时才生成浏览器用例；否则生成检查型用例，步骤改为通用说明，由 tester 在 worktree 里自己读代码、跑命令验证。演示模式保持原样。

### 11. ✅ 并行开发时不管主干：PR 可能带着冲突，测的也不是最终代码

- **现象**：S2T-1 合并后，S2T-2（数据模型）和 S2T-6（归一化规则）并行开发，都会改 `pyproject.toml` 这类公共文件。原来执行阶段结束就直接提交推送、进入测试，不管主干在此期间有没有前进：后合并的 PR 会冲突，自动合并失败时只提示「请手动处理」；测试和评审验证的也是落后于主干的代码。
- **处理**：
  - 提交前先把最新主干合进开发分支。没有冲突就自动合并，测试和评审基于合并后的代码；有冲突就撤销合并、不推送，退回执行阶段，把冲突文件列给开发智能体，由它合并主干、解决冲突后重新汇报。
  - 评审期间主干又前进、导致自动合并（或人点合并）时冲突：自动交回开发智能体解决，最多 2 次，再冲突才交给人。
  - 用本地裸仓库跑真实 git 的测试覆盖了这两种情况。

### 12. ✅ 测试超过 5 分钟，开发智能体就会「掉线」，生命周期断掉

- **现象**：S2T-2、S2T-6 的测试各跑了 20 多分钟。开发智能体汇报「执行完成」后收到 `fetch failed`，重报一次被告知「当前在测试阶段」，于是自己找评审看了一遍、汇报评审又被拒，最后收工。Hub 判定「没走完生命周期」，把工作项打回待办，测试却还在跑。
- **原因**：CLI 通过 MCP 任务桥回调 Hub，`report_phase(do)` 要阻塞到测试结束才返回。任务桥用的是全局 `fetch`（undici），默认 5 分钟收不到响应头就断开。S2T-1 的测试只跑了 80 秒，所以没暴露。
- **处理**：任务桥改用 `node:http`，不设超时；CLI 侧的 MCP 工具超时也放到 24 小时（Claude Code 的 `MCP_TOOL_TIMEOUT`，Gemini 的 MCP 配置 `timeout`，后者默认只有 10 分钟）。「等人确认需求」同样受益，人可能几小时后才回复。

### 13. ✅ 空闲时重启只看工作项主运行，把测试和评审子任务杀了

- **现象**：上一条里两个主运行提前结束后，空闲重启认为「没有运行中的工作项」，立刻重启，把还在跑的 2 个测试任务和 6 个委派出去的评审 / 审计子任务全部中断。
- **处理**：改为等所有未结束的任务（含测试任务、委派子任务）都结束才重启。

### 14. ✅ 重启后测试记录被重新执行，没人等结果

- **现象**：重启时「运行中」的测试会被重新排队并重新执行，但等它结果的开发运行已经随重启中断了。这些测试白跑一遍，工作项重试时还会再排一次。
- **处理**：重启时生命周期里的测试直接取消（标明原因），由工作项重新运行时重新排队；只有人手动发起的测试才重新排队执行。

### 15. ✅ 运行「正常结束」但没走完生命周期，工作项就一直卡在待办

- **现象**：智能体提前收工时，运行状态是「完成」而不是「失败」，工作项被打回待办，但哨兵只自动重试失败的运行。S2T-2、S2T-6 就这样卡住了。
- **处理**：哨兵把「完成但没走完生命周期」也当作需要重试的情况，评论里说明原因。

### 16. ✅ 开发任务占着槽位等测试，测试拿不到槽位：死锁

- **现象**：S2T-2、S2T-6 第 2 轮都卡在测试阶段 50 分钟，测试记录显示「运行中」，tester 任务却一直是「等待中」，一条消息都没有。
- **原因**：Claude Code 底座的并发上限是 2。CLI 任务从启动到结束一直占着一个槽位；两个开发任务都阻塞在 `report_phase(do)` 等测试结果，两个 tester 排队等槽位，互相卡死。委派子任务（`call_agent`）、智能体会话、等人确认需求也有同样的结构。
- **处理**：运行时增加 `waiting()`：任务在 Hub 工具里阻塞等待别的工作（等测试、等委派的子任务、等会话对方发言、等人确认需求）时让出 CLI 槽位，等完再以最高优先级拿回来收尾。测试覆盖并发上限 1 和 2 两种场景；去掉这一步时测试会卡死超时。

### 17. ✅ 基础设施原因的重试会消耗「轮次」，还要从头理解需求

- **现象**：生命周期最多 3 轮，本意是限制「评审不通过、重来」的次数。但重启中断、提前收工后的自动重试也会新开一轮，并从「需求理解」重新开始。S2T-2、S2T-6 因为第 12、16 条已经用掉 2 轮，再被中断一次，评审只要不通过一次就会直接失败。
- **处理**：运行失败、提前收工、重启中断时记下所在阶段，下次运行（哨兵重试或人点运行）从那里继续，不计入轮次；中断在测试阶段的回到执行阶段，代码已在，重新汇报即可触发测试。合并冲突交回开发时也从执行阶段继续。人主动停止、评审不通过仍然新开一轮。

### 18. ✅ 并行 worktree 共用本机服务，测试互相污染

- **现象**：S2T-2 和 S2T-6 并行开发时，都连本机同一个 Postgres 测试库 `s2t_test`。S2T-2 把自己的迁移跑了进去，S2T-6 的迁移测试就对不上了。这不是哪个分支的代码问题，但 Agent Hub 在同一台机器上并行开多个 worktree，这类冲突会经常出现。
- **处理**：
  - Hub 启动 CLI 时注入 `HUB_ISSUE_KEY` / `HUB_ISSUE_SLUG`（当前工作项编号；测试任务取被测工作项，委派的子任务沿任务树取根工作项），以及 `HUB_TASK_ID`。
  - 在 S2T 的「项目知识」里写入约定：有 `HUB_ISSUE_SLUG` 时，测试库、Redis db、端口要按它隔离。项目知识会进入每个智能体的提示词，后续工作项会照此调整测试配置。
- **还可以做**：为每个 worktree 自动分配独立的服务实例（容器）。

### 19. ✅ Hub 不看 GitHub 上真实的 CI 结果

- **现象**：PR #18 的 CI 有一个 job 失败（compose smoke），Hub 却显示「检查通过」，项目负责人的审核意见里也没提。原因是交付后直接把检查状态记成「通过」，只反映 Hub 自己的验收，「测试未通过禁止合并」这条护栏形同虚设。
- **处理**：
  - 交付后先查 PR 最新提交的 check runs，还在跑就最多等 15 分钟。失败或没跑完时护栏拦下，写明是哪个 job。
  - 人点合并时再查一次，CI 失败会拒绝并说明。人确认是 CI 自身的问题后，可以「仍然合并」。
  - 详情页把「Hub 验收」和「GitHub CI」分开显示。
- **顺带**：这次失败本身是 S2T-1 写的 CI 留下的偶发缺陷：后台的 uvicorn 没停，占着 uv 缓存锁。已在 S2T 里提成 bug S2T-17，交给项目负责人分诊。

### 20. ✅ 人批准过的 PR，解决冲突后还要再审一次，越拖越冲突

- **现象**：S2T-6 我审核通过、点了合并，因为和主干冲突没合进去，被交回开发智能体解决。重新交付后，护栏（改动超过 800 行）又拦下要我再审；等我审的时候 S2T-3 先合并了，`uv.lock` 再次冲突。来回两次。
- **处理**：人点合并、因冲突交回开发时记下「已批准合并」。智能体解决冲突、重新交付后，只要 Hub 测试和 CI 都通过就直接合并，不再因为改动大小或受保护路径二次审核；测试或 CI 失败仍然拦下。合并后清掉批准记录。

### 21. ✅ 空闲重启打断了交付收尾，走完流程的工作项被打回待办

- **现象**：S2T-17（修 CI 的 bug）测试、评审都通过，交付说明也写好了，状态却回到待办，哨兵也不重试，卡住了。
- **原因**：运行结束后，Hub 还要异步做交付收尾（回写评论、负责人审核、护栏、合并）。空闲重启只看「有没有运行中的任务」，恰好在收尾期间判定空闲，重启打断了收尾。新进程又把「进行中、但没有运行」的工作项一律当作中断，打回待办。
- **处理**：空闲重启也要等收尾处理完（计入等待数）。启动对账时，生命周期已经走完的工作项进入审核并补做收尾，不再打回待办。

### 22. ✅ 细粒度令牌读不了 CI，Hub 静默当作「没有 CI」

- **现象**：第 19 条上线后，S2T-6 重新交付时 PR 上的 CI 记录是空的，护栏也没生效。
- **原因**：细粒度令牌读 check runs 接口返回 403（Resource not accessible by personal access token），读取失败被静默吞掉，看起来就像仓库没配 CI。
- **处理**：check runs 读不了时改读 GitHub Actions 的运行和 job（细粒度令牌有 Actions 读权限即可），同一工作流被重跑时只看最新一次。两个都读不到时记为「无法读取 CI」并写明原因（提示给令牌加 Actions 读权限），审核意见和详情页都会显示，不再静默。用本机令牌实测：check runs 403，Actions 接口能读到 3 个 job 的实时状态。

### 23. ✅ 人点合并遇到冲突，超过 2 次就只给一句 GitHub 原始报错

- **现象**：S2T-6 被后合入的 S2T-3、S2T-4 先后弄冲突（都改了 `uv.lock`），已经自动交回开发 2 次。第 3 次我点合并时，Hub 直接抛出 `405 Pull Request has merge conflicts`，没有任何后续安排。
- **处理**：「最多自动处理 2 次」只约束负责人发起的自动合并，防止陷入循环；人点合并就是明确要合，总是交回开发智能体去解决，提示是第几次，并说明解决后测试与 CI 通过会直接合并（沿用第 20 条的「已批准」）。没有可交回的开发智能体时，说清楚原因。
- **观察**：并行分支都改依赖锁文件（`uv.lock`）是这几次冲突的共同来源。后续可以考虑：锁文件冲突时由 Hub 在合并主干阶段直接提示智能体「以主干为准、重新生成锁文件」。

### 24. ✅ Hub 在等 CI，界面却叫人去「验收并合并」

- **现象**：S2T-5 交付后，护栏没拦、本该自动合并，「需要你处理」里却出现「验收并合并 PR #24」，CI 一栏是空的。人照着点合并，就绕过了 CI。
- **原因**：交付后 Hub 在等 CI 跑完（第 19 条，最多 15 分钟），这段时间工作项已经是「待审核」，界面又看不到等待状态。
- **处理**：等待期间每次查到的 CI 进度都写进 PR 并推给界面（「CI 进行中：backend」），工作项不出现在「需要你处理」里，结果出来后再自动审核、合并或拦下。

### 25. 📝 订阅登录下，预算熔断按「估算费用」计算，语义不清（低优先级）

- **现象**：开发到 S2T-10 时触发「今日总预算 $50 已用完」，后续工作项全部暂停。今天的估算费用 $53.32，按智能体看 backend-dev $29.1、code-reviewer $9.1、tester $7.9；按工作项看 S2T-6 最多（$8.06，三次冲突来回）。

### 27. ✅ pi 底座用不起来：检测错、接不上 Hub 工具、输出解析不了

- **现象**：用户想把一部分工作交给 pi 上的 GLM、Kimi 订阅分担，但 Agent Hub 显示 pi「供应商未配置 Key」，模型列表里只有 models.json 里自定义的 3 个 Kimi，看不到 GLM。

  - 更关键：pi 的启动命令没接 MCP 桥，pi 智能体拿不到 `report_phase`，一跑就会「没走完生命周期就结束」。pi 只读 `~/.pi/agent/mcp.json` 和项目里的 `.pi/mcp.json`，后者需要 `-a`（信任本次运行的项目文件）。

- **处理**：
  - 登录状态读 `auth.json` 的供应商名（不读内容），模型列表用 `pi --list-models`。

  - 系统提示里说明 Hub 工具在 MCP 服务器 hub 上（pi 的 MCP 工具藏在 codemode 后面）。
  - 解析 pi 的 JSON 事件：对话记录、最终回复、token 用量和费用（订阅渠道费用为 0，不占预算）。
  - 实测：GLM-5.4 通过 codemode 找到并调用了 Hub 的 MCP 工具（26 秒）。
- **上线后又踩到一个坑**：S2T-11 用 pi 跑了 10 分钟一直停在「需求理解」，工具列表里没有 hub。逐项排查（git worktree、嵌套在 agent-hub 目录里、参数顺序、env 传递）都正常，最后定位到配置里的 `timeout`：这个字段是为 Gemini 加的（单位毫秒），pi 的单位却是**秒**（默认 60）。86400000 秒换算成毫秒超出 Node 定时器上限，定时器溢出后立即触发，连接一开始就判定超时失败。改为按秒填 86400（24 小时）。这也说明 pi 默认只等 MCP 工具 60 秒，不设的话「执行完成后等测试」照样会超时。

### 28. 📝 CLI 智能体能读写 worktree 之外的任何文件

### 29. ✅ CLI 智能体运行期间看不到对话记录，像没在干活

- **现象**：S2T-11 交给 pi 上的 GLM 后，界面上 frontend-dev 的「对话记录」一直显示「暂无」，看起来没在干活。实际上它已经通过 Hub 工具查了相关工作项、读了后端接口和 CI 配置。

### 30. ✅ 哨兵会重启「慢但还在干活」的智能体

- **现象**：S2T-11 交给 GLM 后，「执行」阶段到了 42 分钟，心跳一直正常，worktree 里已经有 20 个文件改动。执行阶段的时限是 45 分钟，处理链是「提醒 → 重启 → 改派 → 上报」，而且每次巡检（每分钟）升一级：再过几分钟，哨兵就会把它重启。
- **问题**：「超时」和「卡住」是两回事。慢的模型（或大工作项）很正常，重启只会丢掉正在写的代码。
- **处理**：超时但心跳正常时，只提醒和上报（不打断），两步之间至少隔半个时限，走完不再重复；没有心跳（真卡住）才走重启、改派。提醒的措辞也区分「仍在活动」和「无进展」。当时先把执行阶段时限临时调到 120 分钟，避免 S2T-11 被打断。

### 31. ✅ 哨兵重启撞上服务重启，工作项卡在待办没人管

- **现象**：S2T-11 在评审阶段修 code-reviewer（Kimi）提出的阻塞问题，心跳正常。旧代码的哨兵按 20 分钟时限把它「重启」（正是第 30 条），恰好赶上空闲重启，续跑的运行又被中断。新进程给它记了「从评审阶段续跑」，但最后一次运行显示「已取消」，而哨兵只重试「失败」和「没走完生命周期」的运行，于是一直停在待办。
- **处理**：记了续跑点（基础设施原因中断）的工作项，即使最后一次运行是「已取消」也自动重试，评论里写明从哪个阶段继续；人主动停止的不会留续跑点，不会被自动拉起。

### 32. ✅ 前端改动没有浏览器验收：缺「工作项预览环境」

- **现象**：S2T 的三个前端页面并行开发时，测试阶段只能跑组件测试、类型检查和构建，没人真正打开浏览器点页面。原因有三层：DevEye 没装到 PATH；项目没配测试地址；更根本的是，每个前端改动都在自己的 worktree 分支上，固定的测试地址测到的是主干，不是这次的改动。
- **处理**：
  - 新增「本地预览命令」（项目测试环境里配置）：每次验收前，Hub 在被测工作项的 worktree 里执行它，传入现分配的 `PREVIEW_PORT` / `PREVIEW_API_PORT` 和 `HUB_ISSUE_SLUG`，以前端地址可访问为就绪（最多 3 分钟），验收结束对整个进程组 SIGTERM。多个工作项可同时预览，互不冲突。
  - Hub 托管 DevEye 服务端，为每次验收建一个无头浏览器，tester 的 browser 工具自动指向它；验收结束销毁。有本地预览时浏览器验收可以并行（原来真实 DevEye 只能串行）。
  - 预览没起来时照样交给 tester，并附上原因和日志尾部，由它判断是代码问题（判失败）还是环境问题。
  - 测试设置里新增「DevEye 扩展目录」，项目测试环境里新增「本地预览命令」。
- **安装 DevEye 时踩到的 DevEye 自身问题**，已在 DevEye 仓库分支 `fix/server-daemon-port-isolation` 修复（未提交）：
  1. `deveye server start -d`（后台模式）拉起子进程时只传了端口 / host / socket，丢了 `--extension-path` 等参数，后台服务端永远无法管理浏览器；`restart` 也不保留这些设置。改为转发全部参数，状态文件记下扩展目录等供 `restart` 恢复。
  2. 服务端用非默认端口时，托管浏览器里的扩展仍只连 9888，卡在「waiting for WS」。改为每个托管浏览器加载一份扩展副本，里面写 `deveye-managed.json`（host / 端口 / 令牌），扩展启动时优先读它，从安装那一刻就连对端口。
  3. 所有服务端共用一套状态文件（`$TMPDIR/deveye-server.pid/.json/.log`）和默认 socket，多开会互相覆盖，第二个端口上的 `start` 甚至会误报「已在运行」；DevEye 自己的服务端测试也会删掉用户正在用的状态文件。改为非默认端口的状态文件和 socket 按端口独立，`status` / `stop` / `restart` 增加 `--port`；socket 路径过长时给出明确报错（原来是 `listen EINVAL`）。
  - 验证：新增 6 个测试；CLI 包 1066 通过（7 个失败与改动前相同，均为已有问题），根目录 1649 通过；实机验证后台模式 + 9899 端口建浏览器、打开页面、`restart` 后仍可建浏览器、默认端口状态不受影响。
  - Hub 侧随之改回专用端口 9899 托管 DevEye，不占用用户默认的 9888。

### 33. ✅ 跑过几轮的工作项，失败后不再被自动重试

- **现象**：S2T-19 解决主干冲突的那次运行没走完生命周期就结束了，哨兵重试的运行又被服务重启打断，之后一直停在待办。
- **原因**：自动重试的上限按「这个工作项总共跑过几次」算（默认重试 1 次 → 总次数超过 2 就不再重试）。S2T-19 之前正常交付过一轮、又解决过一次冲突，总次数早就超了。
- **处理**：改为按「最近连续失败几次」算：服务重启造成的中断不算失败，遇到正常完成的运行就停止往前数，最近一次「完成但没走完生命周期」算一次。

### 34. ✅ CI 没过就停在人这里，不会交回开发修复

- **现象**：S2T-20（模型调用与 SSE 加全局并发上限）交付后，CI 的 compose smoke 失败（后端在 CI 里没能启动），护栏拦下后只是等人；同时它又和主干冲突，GitHub 不再给它跑新的 CI。

### 35. ✅ 浏览器验收依赖外部的专有工具 DevEye

- **现象**：浏览器验收要先单独安装 DevEye，还要配置扩展目录、托管服务端，装的时候又踩了 DevEye 自身的三个问题（第 32 条）。想把 DevEye 直接并进 Agent Hub，但 DevEye 是专有软件（禁止修改和再分发），而 Agent Hub 是 MIT 开源项目，不能合并。
- **处理**：Agent Hub 自带浏览器驱动（`src/browser.ts`），基于 playwright-core（Apache-2.0）驱动本机 Chrome，不下载浏览器：

  - snapshot 给可见的可交互元素编号，带上表单标签、当前值（密码不回显）、页面上的提示文字；点击、输入后等网络安静再返回新快照，省一次 snapshot；
  - 每次验收一个独立的浏览器上下文，共用一个 Chrome 进程，可并行；控制台消息补上出错的资源地址；

- **验证**：用 S2T 主干的预览环境实测，内置驱动登录后进入工作台，导航、按钮识别正确，控制台和网络检查、截图正常。

### 36. ✅ 模型订阅额度用完，被当成普通失败

- **现象**：S2T-12、13、14 三个前端页面都跑在 pi 的 GLM 上，同时报 `429 Usage limit reached for 5 hour. Your limit will reset at 2026-11-26 16:16:42`。哨兵按普通失败重试一次，立刻又是 429，之后就不再管了；连续失败计数也被占掉。
- **处理**：
  - 识别额度 / 限流类报错（usage limit、rate limit、quota、429 等），解析恢复时间：`reset at <时间>`、ISO 时间、Claude Code 的 `limit reached|<unix 秒>`、`try again in 30 minutes`；认出是额度问题但没给时间时，按 15 分钟后再试。
  - 这类失败不计入连续失败次数；哨兵等到恢复时间之后再从原阶段续跑，不消耗轮次。
  - 工作项评论写明「额度用完，预计几点恢复后自动继续」，并提示着急时可以换模型；列表里显示「⏸ 等额度 16:16」。
- 这次是手动把 frontend-dev 临时切到 Claude Code 先跑起来的；以后可以考虑给智能体配一个备用底座，额度用完时自动切换。

### 37. ✅ 测试写得越多，越容易被「改动行数上限」拦下

- **现象**：S2T-14（工单中心页面）改动 4997 行被护栏拦下，其中测试代码约 2800 行（列表、详情、筛选、组件测试和接口 mock）。护栏想限制的是人要评审的业务代码，测试写得充分反而吃亏。
- **处理**：统计改动行数时识别测试文件（`__tests__/`、`tests/`、`*.spec.*`、`*.test.*`、`test_*.py`、`*_test.go`、`conftest.py` 等），PR 上单独记下测试行数；护栏的行数上限扣掉测试，拦截提示写成「改动 N 行（另有测试代码 M 行，不计入）」（最初写成「不含测试 M 行」，容易被读成 M 是业务代码行数，S2T-13 上线后改了措辞）。锁文件早就不计入（第 6 条），子目录里的也会排除。

### 38. ✅ 代码没提交成功，却一路走到「待最终验收」

- **现象**：S2T-13（对话工作台）走完了测试和评审，停在「等你最终验收」，但没有 PR，分支也没推到 GitHub。
- **原因**：
  1. 判断「有没有要提交的内容」用的是 `git status --porcelain`，它把未跟踪的 `.pi/`（Hub 写的 pi MCP 配置，含任务令牌，故意不提交）也算进去。智能体自己已经提交过代码，暂存区是空的，`git commit` 因 nothing to commit 失败。
  2. 提交失败的消息只返回给了智能体，没有写进工作项；流程照常进入测试和评审。
  3. git 把 nothing to commit 写在 stdout，Hub 只取 stderr，报错里看不到原因。
- **处理**：改用 `git diff --cached` 判断暂存区；git 报错时 stderr 为空就取 stdout；提交或推送失败时留在执行阶段，在工作项里写明原因，让智能体处理（解决不了就报 blocked），不再带着没有 PR 的改动进入测试。
- **兜底**：交付时（以及服务启动时）发现项目关联了仓库、生命周期走完却没有 PR，自动退回「执行」阶段续跑一次，重新提交并测试、评审；再缺就交给人。S2T-13 就是这样补救的。

### 39. ✅ 换成便宜模型后，Kimi 并发上限把一半工作项打成失败

- **现象**：执行层改到 pi（GLM 5.4 / Kimi K3.1 Pro）后，S2T-24、27、34 同时报 `403 You've reached your concurrent request limit ... access_terminated_error`。哨兵按普通失败重试一次又撞上，就停了；S2T-32 的前两轮测试也因 tester 撞上同一个限制而失败。
- **原因**：pi 底座的并发上限是 4，但 Kimi 订阅只允许很少的并发请求，同一底座下不同厂商的限制不一样；「并发超限」也不在网络抖动的识别范围里。
- **处理**：
  - 同一底座可以按模型厂商单独限并发（如 pi 下 `kimi-coding` 只开 2 个）。排厂商的队时不占底座槽位，不会把 GLM 的任务也堵住。
  - 「concurrent request limit」算可重试的抖动。
  - **兜底换模型**：智能体的模型用不了（额度用完、并发超限、鉴权失败、厂商故障）时，按兜底链（默认 GLM → Kimi → Claude Code）换下一个能用的重跑这一步，并在工作项里留言。用不了的模型冷却一段时间（额度按恢复时间，并发 2 分钟，鉴权 30 分钟），这期间新任务直接走兜底，不再先失败一次。同一底座内换模型会续原来的会话；跨底座则开新会话。
- Kimi 只留给 tester 一个智能体用（验收一次只跑一个，正好适合低并发），其余执行层用 GLM。

### 40. ✅ 并行的 PR 各自 CI 都通过，合在一起却是坏的

- **现象**：S2T-32、35、37 并行开发，各加了一个数据库迁移，都叫 0007、都接在 0006 后面。三个 PR 各自的 CI 都通过，GitHub 也显示可以合并。合并任意两个，主干上就会出现两个迁移头，迁移直接失败。
- **原因**：每个 PR 的 CI 都是对着开工时的主干跑的。先合进去一个之后，其余 PR 的 CI 结果就过时了，但 Hub 合并前只看 CI 状态，不看分支是否包含最新主干。
- **处理**：合并前先比较 PR 是否落后主干。落后时调用 GitHub 的 Update branch 把主干合进分支，等 CI 对合并结果重新跑完再合并；CI 不过就交回开发修复（视为已批准，修好后直接合）；有冲突就走原来的冲突处理。这次是我人工发现的，先合了 S2T-37，再留言让另外两个重新编号。

### 41. ✅ 智能体自己推过分支，Hub 推送被拒（stale info）

- **现象**：S2T-32、35 交付时报 `! [rejected] HEAD -> agent/s2t-32 (stale info)`。
- **原因**：Hub 按仓库地址推送，本地没有对应的远端跟踪分支，裸的 `--force-with-lease` 拿不到准确的预期值；智能体在执行阶段自己推过这个分支，于是被拒。
- **处理**：推送前先用 `ls-remote` 查远端分支当前的提交，用 `--force-with-lease=<分支>:<该提交>`。远端没被别人改过就照常推送，包括覆盖智能体自己推的旧提交。

### 42. ✅ 第二期的工作项普遍超过行数上限，全部停在人这里

- **现象**：第二期的工作项体量大，S2T-32、35、37 扣掉测试后仍有 1100～2300 行，而且都带数据库迁移（受保护路径）。测试、CI、代码评审、安全审查全部通过，却都停在「等你确认合并」。
- **处理**：护栏新增可选的「资深评审代替人放行」。只因改动超限，或涉及允许的受保护路径（如 `**/migrations/**`）被拦、且测试与 CI 通过时，交给指定的智能体（用最强的模型）对整个 PR 做一次资深评审，重点看迁移冲突、鉴权、并发与幂等。结论通过就自动合并，需要修改就带着意见交回开发；每个工作项最多 2 次，之后交给人。其余受保护路径（`.github/**`、`infra/**`、支付）仍然要人确认。默认关闭，S2T 项目已开启，评审人是 code-reviewer（Claude Opus）。

### 43. ✅ 负责人每 5 分钟巡检一次，把 Claude 的 5 小时额度用光了

- **现象**：凌晨 S2T-32、34、35、38、39、40 同时报 `You've hit your 5-hour limit · resets 3:50am (Asia/Shanghai)`，全部停在「上次失败」。
- **原因**：
  1. 项目是自动驾驶模式，只要进行中的工作项少于 2 个，project-lead（Claude Opus）就每 5 分钟开一次完整会话做例行巡检（一天最多 20 次），工作项列表没有变化也照跑。执行层的兜底链最后一站又是 Claude，额度很快用完。
  2. Claude Code 的额度提示 `hit your 5-hour limit · resets 3:50am (Asia/Shanghai)` 不在识别范围内：没有当作额度问题等恢复，兜底也不知道 Claude 暂时用不了，只能直接报失败。
- **处理**：
  - 例行巡检在三种情况下跳过：上次巡检还没结束、距上次不到 30 分钟、工作项状态和上次巡检时完全一样（比较的是状态指纹）。
  - 识别 `hit your … limit`，按 `resets 3:50am (时区)`、`resets Mon 9am (时区)` 算出恢复时间（支持时区，取下一次出现的时刻），之后按额度等待或换模型处理。
